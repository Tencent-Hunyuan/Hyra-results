# hyqec: certified distances of quantum stabilizer codes

Technical report: [paper/HyQEC_Technical_Report.pdf](paper/HyQEC_Technical_Report.pdf).

**hyqec** computes the distance of a quantum stabilizer code, general (non-CSS) or CSS, and
backs every answer with evidence that someone else can re-check. It finds light logical
operators (upper bounds) and *proves* that no lighter one exists (lower bounds). Its main use is
the exact Pauli-weight distance of non-CSS codes, where the usual tools give only heuristic
upper bounds.

The folder holds two separately written Python packages:

| package | version | role |
|---|---|---|
| [`hyqec-verify/`](hyqec-verify/) | 0.3.0 | the prover: upper-bound search, branch-and-bound (CPU/GPU), SAT with DRAT proofs, certificates, `verify` |
| [`hyqec-check/`](hyqec-check/) | 2.0.2 | an **independent checker** for branch-and-bound coverage certificates, implemented from the written specification without reading or importing the prover's code |

## Result

The [qldpc-challenge](https://github.com/unitaryfoundation/qldpc-challenge) board lists 184
general (non-CSS) stabilizer codes. It labels every one of them as an upper bound (`d≤`) only,
because its certifier does not minimise Pauli weight (its `TRACKS.md`, checked on 2026-10-27).
Exact non-CSS distances have been computed elsewhere for other instances, for example by Lee et
al. ([arXiv:2609.30069](https://arxiv.org/abs/2609.30069)). The count here is about this board.
With hyqec, **165 of the 184 board codes have a proven exact distance**. Every value equals the
board's claimed distance.

| evidence level | codes | what was run |
|---|--:|---|
| SAT proof checked by `drat-trim` (the CNF encoding is hyqec's own), plus branch-and-bound | 122 | CPU, 300 s, 8 threads |
| branch-and-bound search record (re-executable by the same prover; not independently checked) | 29 | CPU, 300 s, 8 threads |
| GPU branch-and-bound search record (re-executable by the same prover; not independently checked) | 13 | 1 GPU, 30 min |
| coverage certificate **re-executed by the independent checker** (board [[452,115,18]]) | 1 | see below |
| still open (bounds only) | 19 | |

Only the last kind of proof is checked by an independent implementation of the whole argument.
`drat-trim` checks each SAT refutation, but the CNF that encodes "a logical of weight ≤ W
exists" is generated by hyqec-verify itself.

Codes are from the board snapshot of 2026-10-16 (commit `2f1f65ea`). The runs used a pre-release
build of hyqec-verify. They are engine-only: no input witness was used as a lower bound and the
brute-force shortcut was off. The accompanying technical report reports 178 exact distances among
the 187 entries of a later snapshot (2026-10-18, commit `fa4b0de3`). Those come from longer runs of
the research versions of the tools, up to about 10^14 search nodes and tens of hours per code. The
165 here are what the sweep above proved within its per-code budgets. The report's other 13 (3 entries
new in the later snapshot and 10 that exceeded the budgets) used only methods that hyqec-verify
0.3.0 also provides, so in principle it can prove them with longer runs; this is untested, and we
estimate about 35 h on 8 GPUs, mostly for [[336,10,28]].

**Largest certified instances.** Both codes are public, and each certificate was re-executed in
full by hyqec-check, with 0 mismatches:

| code | statement | certificate | prover time (with certificate) | checker time |
|---|---|---|---|---|
| board [[452,115,18]] | no logical of weight ≤ 17, so **d = 18** (board witness of weight 18) | 2,282,025 tasks, 124,648,548,270 nodes | 315 s on 6 H20 GPUs | 25 min on 128 CPU threads |
| Lee et al.'s [[452,115,18]] instance `o04829` ([arXiv:2609.30069](https://arxiv.org/abs/2609.30069)) | no logical of weight ≤ 17 (re-certifies their d = 18) | 254,720 tasks, 299,674,975,243 nodes | 324 s on 4 H20 GPUs | 68 min on 128 CPU threads |

Without a certificate, the [[452,115,18]] proof takes 120 s with the shipped defaults on 6 H20
GPUs. The certificates (95 MB and 10.5 MB uncompressed) are **not included in this release**.
Anyone can regenerate them from the public code files with `hyqec-verify lower ... --bnb-cert`.

**Head-to-head against dist-m4ri v0.14.7.** Both tools were given the same matrix, the same
target and the same symmetry, and ran at the same time on disjoint 64-core sets:

- On the board's [[452,115,18]], hyqec proves "no logical ≤ 17" in **1,234 s**. In its 2 h cap,
  dist-m4ri gets only as far as "no logical ≤ 13".
- On small dense codes, dist-m4ri is the better tool. Of the 8 codetables codes measured head
  to head (n ≤ 50), dist-m4ri was faster on 7, by 1.2–109×, and by at least 12× on each of those
  where our run took more than 1 s. The eighth, [[41,2,11]], is a tie. The B&B packing bound barely prunes on dense codes:
  on the 9 codetables codes with n ≤ 53, each +1 in the target weight costs 7.6–16.7× more
  nodes, against 2.7–6.5× on 29 sparse codes.

Details: [`hyqec-verify/docs/benchmarks.md`](hyqec-verify/docs/benchmarks.md),
[`hyqec-verify/docs/related_work.md`](hyqec-verify/docs/related_work.md).

- **[[488,123,22]]**, a code of our own construction that is not on the board. A coverage
  certificate for "no logical of weight ≤ 21" (20,324,715 tasks, 3,157,706,215,314 nodes; 3.6 h

## What is and is not certified

| evidence | proves | re-checked by |
|---|---|---|
| witness | `d ≤ w` | linear algebra in `hyqec-verify verify` (milliseconds) |
| SAT + DRAT proof | `d ≥ W+1` | `verify` regenerates the CNF from the code and re-runs the bundled `drat-trim` (optionally LRAT + `lrat-check`) |
| B&B **coverage certificate** | `d ≥ W+1` | **hyqec-check**, a separate implementation (`verify --bnb-checker auto`) |
| B&B search record without certificate | `d ≥ W+1` | only by re-running the same prover (`verify --rerun-bnb`); weaker evidence, and labelled as such |

- A coverage certificate proves a **lower bound** ("no nontrivial logical of weight ≤ cap in
  domain P, X or Z"). An exact distance also needs a witness of weight cap + 1.
- Checking a certificate costs about as much search as producing it. The trace hash is
  non-cryptographic and is never accepted on its own.
- The certificate formats are written down: [`BNB_CERT_SPEC.md`](hyqec-check/docs/BNB_CERT_SPEC.md)
  (container v1, revision 1.1) and [`BNB_CERT_SPEC_v2.md`](hyqec-check/docs/BNB_CERT_SPEC_v2.md)
  (container v2, revision 2.0-rc1, for the opt-in S0/S1/S2 pruning rules). The checker's `hyqec-check`
  and `hyqec-check-wide` commands implement v1; `hyqec-check-v2` implements v2 and re-derives
  and verifies every prune. `hyqec-verify verify --bnb-checker auto` picks the matching checker for
  either version.
  The v1 specification is kept byte-for-byte, because the checker pins its hash, so its status line
  ("Independent wide-limit validation is pending") predates that validation. The checker's wide
  profile has since accepted real certificates for two codetables codes whose generators exceed
  the original weight-32 limit: [[53,6,11]] and [[80,7,15]], at caps 2 and 3.
- What has to be trusted for each kind of evidence:
  [`hyqec-verify/docs/SOUNDNESS.md`](hyqec-verify/docs/SOUNDNESS.md).
- The B&B search itself is not new. It follows the irreducible-cluster method of Dumer, Kovalev
  and Pryadko (IEEE Trans. Inf. Theory 63, 4675 (2017)) and is close to the general-stabilizer
  B&B of Lee et al. (arXiv:2609.30069, App. B.2). hyqec adds verified symmetry, identical CPU and
  GPU search trees, checkpointing, independently checkable certificates and SAT/DRAT
  cross-checks.

**Reviews and testing.**

- **Checker v1 code review.** An independent code review of the v1 checker found no blocker. The
  reviewer's own spec-only certificate writer, run on about 1,200 random codes, gave
  4,990/4,990 correct accepts and 4,656/4,656 rejections of forged certificates. Every
  single-byte mutation of the record stream (5,140) was rejected, and so was every truncation
  (5,261). About 120 semantic attacks were all handled correctly. A later review of the 1.2/1.3
  changes found no blocker.
- **Checker v2 conformance.** v2 matched all 56 exported conformance artifacts, all 42,250
  canonical node vectors, the 7 VERIFY cases and the node totals of 888 complete searches
  (2,396,942,083 nodes). An independent specification and code review found no blocker. See
  [`hyqec-check/docs/PUBLIC_VALIDATION.md`](hyqec-check/docs/PUBLIC_VALIDATION.md).
- **Prover reference suite.** The prover was tested against an independent reference suite of
  300 cases (n ≤ 63), with each engine alone. 263 matched an independent oracle's distance or
  the expected handling of an adversarial input. 37 lay in the reference interval. There were 0
  failures.
- **Prover acceptance.** The black-box acceptance of the first release (0.1.0) on 388 reference
  codes had 0 failures, errors or timeouts, and all 774 emitted certificates reproduced.
- **Pruning-rule audit.** The opt-in pruning rules are audited on 2,000 random codes. Every
  pruning cut is checked against exhaustive logical enumeration, with none sampled; see
  [`hyqec-verify/tests/native/PRUNING_AUDIT.md`](hyqec-verify/tests/native/PRUNING_AUDIT.md).

## Install

Linux, Python ≥ 3.10, a C/C++ compiler and zlib headers (`zlib1g-dev` / `zlib-devel`). CUDA is
optional.

```sh
cd AI4Science/hyqec
python3 -m venv .venv && . .venv/bin/activate
pip install ./hyqec-verify ./hyqec-check
pip install './hyqec-verify[nauty]'   # optional: nauty symmetry detection (pynauty), used in the reported runs
hyqec-verify tools install   # optional: builds pinned Kissat and CaDiCaL (git + make; downloads from GitHub)
hyqec-verify build           # optional: compiles the native CPU engines now (otherwise on first use)
hyqec-verify doctor          # what is available
```

To install with GPU engines, also run
`hyqec-verify build bnb-cuda ris-cuda --cuda-arch native` (needs `nvcc`).

## Quick start

```sh
hyqec-verify info code.json
hyqec-verify distance code.json --engines bnb --bnb-cert -o cert.json   # exact d, with a coverage certificate
hyqec-verify verify cert.json --bnb-checker auto --threads 4            # independent check with hyqec-check
hyqec-verify distance code.json --engines bnb --cross-check sat -o cert.json   # two lower-bound proofs by different engines
hyqec-verify lower code.json --engine bnb --bound 17 --bnb-cert -o cert.json   # prove d >= 18 only
hyqec-verify distance css.json --side X                                 # CSS X-distance
```

Input formats: qldpc-challenge JSON (`stabilizer` or `CSS`), a generator JSON, `.npz` (`S`,
`A`/`B`, or `HX`/`HZ`), or one Pauli per line. More in
[`hyqec-verify/README.md`](hyqec-verify/README.md).

## Reproduce small examples (minutes, CPU only)

```sh
bash examples/run_examples.sh out/          # tiny codes: B&B + certificate + independent check, SAT/DRAT if installed
bash examples/board_452.sh out/ 12          # downloads the board's [[452,115,18]] (pinned commit) and proves d >= 13
```

Measured on 6 CPU threads: `run_examples.sh` takes under a minute. For `board_452.sh`, cap 12
takes about 11 s to prove plus 12 s to check. Cap 13 takes about 43 s to prove. Each further
cap costs about 4× more. The full d = 18 proof (cap 17) needs hours on CPU, or minutes on GPUs.

Test suites:

```sh
(cd hyqec-check && make -j4 && make test)
# the prover's referee tests use the built checker; GPU tests skip without a GPU
(cd hyqec-verify && HYQEC_TEST_BNBCHECK=$PWD/../hyqec-check python -m pytest -q tests)
# optional: HYQEC_TEST_UPSTREAM=<qldpc-challenge checkout> also runs the tests that use the board's [[452,115,18]]
```

## Names and formats

hyqec-verify was developed under the working name *stabcert*. File formats keep their historical
ids (`stabcert-certificate/1`, `stabcert-bnb-coverage/1` / `SBCOV1`, `stabcert-bnb-coverage/2`, …)
because these ids are hashed into existing certificates. The same goes for the native engine
names (`stabcert-bnb`, `stabcert-ris`).
